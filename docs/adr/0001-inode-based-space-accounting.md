# 空间计量以 inode 为准，名义大小仅作对照

微信会把同一份内容以硬链接形式挂在多个月份目录下：`msg/file` 的 180 个文件里有 49 个共享 inode，其中 `范春雨V6.0.pdf` 一份内容挂了 5 个名字。若按路径累加，会得出 588.5 MB 的占用，而按 inode 归并后只有 513.2 MB——33 万字节级的差值是虚构的。

我们决定：**实占大小一律按 inode 归并计算**，名义大小只在「硬链接重复」视图里作为对照出现，并且在该视图里明确写出「删除这些副本释放 0 字节」。

不这么做的代价是产品会给出错误的承诺：用户以为删掉 4 份重复简历能腾出空间，实际一字节没变。而这类错误在 UI 上极难被察觉，只有做过 inode 对比的人才会发现。

## Considered Options

- **按路径累加**：实现最简单，但会系统性地高估占用，并让「清理」变成假承诺。
- **按内容哈希归并**：能同时覆盖硬链接与真重复，但对 5 GB 数据做全量哈希需要分钟级时间，且把「同一份数据挂了多个名字」和「两份独立拷贝」混为一谈——这两件事对用户的含义完全不同。
